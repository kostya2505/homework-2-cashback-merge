# Проект 2. Cashback Merge

Мини-игра в духе 2048 на поле `4x4`. На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.

Но у проекта есть второй, продуктовый слой. По итоговой плитке начисляется
награда, и эта награда стоит компании денег. Поэтому максимальную награду
должна получать ограниченная доля игроков — например, не больше `20%`.
Проверяется это симуляцией на тысячах «игроков» до запуска акции.

Задание разбито на три merge request'а. Делай их по очереди.

## Состояние на MR1

Реализованы модель игры, конфигурация кампании, воспроизводимое по seed
начальное состояние и текстовый вывод поля. Движение, объединение плиток
и симуляция появятся в MR2 и MR3.

### Что уже есть

- **домен**: `Tile`, `Position`, `Direction`, `Board`, `GameState`.
- **Конфиг**: `GameConfig`, `SpawnRule`, `Probability`, `ConfigLoader`,
  `JsonConfigLoader`.
- **Игра**: `GameFactory` — создаёт начальное состояние по seed.
- **Спавн**: `WeightedSpawner` — взвешенный категориальный выбор плитки.
- **Рендер**: `BoardRenderer` — ASCII-сетка.
- **CLI**: `Main` — читает конфиг, рендерит стартовое поле.

### Запуск

```bash
# Из корня проекта
./gradlew run
```

По умолчанию берётся конфиг `config/campaign.example.json` и seed `42`.

С явными параметрами:

```bash
./gradlew run --args="--config config/campaign.example.json --seed 42"
```

Вывод: путь к конфигу, seed, размер поля, лимит ходов, ASCII-представление
стартового поля, оставшиеся ходы, счёт (в MR1 — `0`).

### Конфигурация кампании

Формат — JSON:

```json
{
  "boardSize": 4,
  "movesLimit": 100,
  "spawnRules": [
    { "cashback": "1", "probability": "0.85" },
    { "cashback": "2", "probability": "0.15" }
  ],
  "rewardTable": [ ... ],
  "maxRewardCashback": "32",
  "maxRewardAllowedRate": "0.20"
}
```

Поля, которые читает загрузчик:

| Поле | Смысл | Ограничения |
|---|---|---|
| `boardSize` | размер поля `boardSize x boardSize` | положительное целое |
| `movesLimit` | лимит изменивших поле ходов | `> 0` |
| `spawnRules` | непустой массив правил появления | сумма `probability` строго `1.0` |
| `spawnRules[].cashback` | процент кэшбэка новой плитки | целое `> 0`, строкой |
| `spawnRules[].probability` | вероятность появления | десятичная строка в `(0; 1]` |

Секции `rewardTable`, `maxRewardCashback`, `maxRewardAllowedRate` в MR1
игнорируются — они относятся к MR3, и их модель появится вместе с
симуляцией.

### Тесты

```bash
./gradlew check
```

Обязательные тесты MR1:

- `ConfigValidationTest` — валидация конфига (пустые правила, неверная
  сумма вероятностей, `movesLimit <= 0`, границы поля).
- `SeedTest.sameConfigAndSeedProduceSameInitialBoard` — одинаковый
  конфиг и seed дают одинаковое начальное поле.
- `TemplateSmokeTest` — программа стартует без аргументов с кодом `0`;
  пример конфига — валидный JSON.

## Решения, принятые в MR1

### Точная арифметика вместо `double`

Вероятности и проценты кэшбэка хранятся без потери точности:

- `Tile.cashbackPercent` — `int`, проценты в целых числах.
- `Probability` — `long` в масштабе `10^9`. Десятичная строка
  (`"0.85"`) парсится через `BigDecimal` и переводится в целые единицы
  масштаба.
- Сумма вероятностей в `GameConfig` проверяется точным сравнением
  `units == Probability.SCALE`, без `==` над `double`.

Это закрывает требование «храните проценты и вероятности без потери
точности» и исключает классическую ловушку `0.85 + 0.15 != 1.0`.

### Иммутабельные value-объекты

`Tile`, `Position`, `Board`, `GameState` — immutable. Изменяющие
операции (`withTile`, `withoutTile`, `afterMove`) возвращают новые
значения. Это:

- делает состояние партии безопасным для параллельных симуляций в MR3;
- упрощает сравнение «до/после» в тестах на движение;
- даёт бесплатный `equals`/`hashCode` для `record`'ов.

`Board` внутри хранит `int[]`, где `0` — пустая клетка, положительное
значение — процент. Плюсы: нет nullable-элементов,
меньше аллокаций `Tile` в пути симуляции. Наружу `Board` отдаёт
`Optional<Tile>`, `List<Tile>`, `int maxTilePercent()`.

### Конфиг и домен — разные слои

JSON-схема конфига (`boardSize`) не совпадает с моделью (`GameConfig`
с `rows` и `cols`). Трансляцию делает `JsonConfigLoader` — единственное
место, где формат JSON зафиксирован. `Board`, `Position`, `index()`
работают с прямоугольной моделью.

### Вся случайность — через `RandomGenerator`

`GameFactory.createInitial(config, random)` принимает `RandomGenerator`,
а не создаёт `Random` внутри. То же — `WeightedSpawner.choose(random)`.

- **Воспроизводимость.** `new Random(seed)` дважды даёт одинаковое
  начальное поле — это проверяет `SeedTest`.
- **Тестируемость.** В тестах можно подсунуть фиксированный генератор.
- В коде нет вызовов `new Random()` без seed и `Math.random()`.
  Это правило важно и для MR3: отчёт симуляции должен быть
  воспроизводим по `--seed`.

### Слои и зависимости

- `domain` не зависит ни от чего, кроме JDK.
- `config` читает JSON и конструирует `GameConfig`; зависит только
  от `domain` и Jackson.
- `spawn`, `game`, `render` зависят от `domain`.
- `Main` — тонкая точка входа: связывает загрузчик, фабрику и рендер.

`ConfigLoader` — интерфейс, `JsonConfigLoader` — его реализация.
Если в MR3 потребуется читать симуляционный конфиг из другого
источника (например, из DTO), появится второй загрузчик, не ломая
существующий код.
