# Проект 2. Cashback Merge

Мини-игра в духе 2048 на поле `4x4`. На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.

Но у проекта есть второй, продуктовый слой. По итоговой плитке начисляется
награда, и эта награда стоит компании денег. Поэтому максимальную награду
должна получать ограниченная доля игроков — например, не больше `20%`.
Проверяется это симуляцией на тысячах «игроков» до запуска акции.

Задание разбито на три merge request'а. Делай их по очереди.

## Состояние на MR2

Реализованы модель игры, конфигурация игры, движок ходов (сдвиг,
слияние, лимит ходов, подсчёт очков), воспроизводимое по seed начальное
состояние и текстовый вывод поля. Симуляция и награды появятся в MR3.

### Что уже есть

- **Домен**: `Tile`, `Position`, `Direction`, `Board`, `GameState`.
- **Конфиг**: `GameConfig`, `SpawnRule`, `Probability`, `ConfigLoader`,
  `JsonConfigLoader`.
- **Движок ходов**: `SlideEngine` — логика сдвига и слияния,
  `GameEngine` — драйвер партии с лимитом ходов и спавном, `SlideResult`,
  `MoveResult`.
- **Игра**: `GameFactory` — начальное состояние по seed.
- **Спавн**: `WeightedSpawner` — взвешенный категориальный выбор плитки.
- **Рендер**: `BoardRenderer` — ASCII-сетка.
- **CLI**: `Main` — читает конфиг, рендерит поле, по флагу `--moves`
  применяет последовательность ходов.

### Запуск

```bash
# Из корня проекта
./gradlew run
```

По умолчанию берётся конфиг `config/campaign.example.json` и seed `42`.
Без `--moves` программа печатает стартовое поле и завершается.

С явными параметрами:

```bash
./gradlew run --args="--config config/campaign.example.json --seed 42"
```

С последовательностью ходов:

```bash
./gradlew run --args="--moves LEFT,UP,RIGHT,DOWN"
```

После каждого изменившего поле хода печатается новое состояние поля,
оставшиеся ходы и счёт. Ход без изменений помечается `(без изменений)`
и не расходует лимит.

### Конфигурация кампании

Формат — JSON:

```json
{
  "boardSize": 4,
  "movesLimit": 100,
  "spawnRules": [
    { "cashback": "1", "probability": "0.85" },
    { "cashback": "2", "probability": "0.15" }
  ],
  "rewardTable": [ ... ],
  "maxRewardCashback": "32",
  "maxRewardAllowedRate": "0.20"
}
```

Поля, которые читает загрузчик:

| Поле | Смысл | Ограничения |
|---|---|---|
| `boardSize` | размер поля `boardSize x boardSize` | положительное целое |
| `movesLimit` | лимит изменивших поле ходов | `> 0` |
| `spawnRules` | непустой массив правил появления | сумма `probability` строго `1.0` |
| `spawnRules[].cashback` | процент кэшбэка новой плитки | целое `> 0`, строкой |
| `spawnRules[].probability` | вероятность появления | десятичная строка в `(0; 1]` |

Секции `rewardTable`, `maxRewardCashback`, `maxRewardAllowedRate` сейчас
игнорируются — их модель появится вместе с
симуляцией.

## Как работает ход

Движок разделён на два слоя.

### `SlideEngine.apply(board, direction)` — чистая функция

Компактит плитки к стороне движения, сливает соседние равные пары,
возвращает `SlideResult` с новой доской, очками за ход и признаком
`changed`. Ничего не знает про seed, лимит ходов и спавн.

Слияние идёт от края, к которому направлено движение, и каждая пара
сливается не более одного раза:

- `[1, 1, 1, _]` влево → `[2, 1, _, _]`
- `[1, 1, 1, 1]` влево → `[2, 2, _, _]`
- `[2, 2, 4, 4]` влево → `[4, 8, _, _]`

Если ни одна плитка не сдвинулась и не слилась, `SlideEngine` возвращает
тот же объект `Board`, что был на входе, и `changed = false`.

### `GameEngine.applyMove(state, direction)` — драйвер партии

Вызывает `SlideEngine`. Если доска изменилась:

- уменьшает `movesRemaining` на один;
- прибавляет заработанные очки к `state.score`;
- спавнит ровно одну новую плитку через `WeightedSpawner` и переданный
  `RandomGenerator`.

Если доска не изменилась — возвращает `MoveResult.unchanged(state)`
с тем же объектом `GameState`: лимит не тратится, плитка не появляется.

### Score

За каждое слияние в этом ходу начисляется значение получившейся плитки.
Сумма за ход прибавляется к общему счёту `GameState.score`. Сдвиги без
слияний очков не дают.

Плитка `32%` не завершает игру: партия идёт до исчерпания лимита
изменивших поле ходов.

## Решения, принятые в MR1 и MR2

### Точная арифметика вместо `double`

Вероятности и проценты кэшбэка хранятся без потери точности:

- `Tile.cashbackPercent` — `int`, проценты в целых числах;
- `Probability` — `long` в масштабе `10^9`, парсится через `BigDecimal`;
- сумма вероятностей в `GameConfig` проверяется точным сравнением
  с `Probability.SCALE`.

Это исключает классическую ловушку `0.85 + 0.15 != 1.0`.

### Иммутабельные value-объекты

`Tile`, `Position`, `Board`, `GameState`, `SlideResult`, `MoveResult` —
immutable. Изменяющие операции возвращают новые значения. Это упростило
тесты на merge (сравнение «до/после») и сделает состояние партии
безопасным для параллельных симуляций в MR3.

`Board` внутри хранит `int[]`, где `0` — пустая клетка, положительное
значение — процент. Плюсы: нет nullable-элементов, меньше аллокаций
`Tile` в горячем пути симуляции. Наружу — `Optional<Tile>`, `List<Tile>`,
`int maxTilePercent()`.

### Разделение `SlideEngine` и `GameEngine`

Чистая логика хода отделена от stateful-драйвера с RNG. Это даёт:

- тривиальные тесты на четыре примера из ТЗ — без seed, без конфига;
- возможность в MR3 использовать `SlideEngine` из симуляции, не
  поднимая `GameEngine`;
- контракт «несовершённый ход не меняет состояние», проверяемый через
  reference equality (`MoveResult.unchanged(state)` возвращает тот же
  объект).

### Вся случайность — через `RandomGenerator`

`GameFactory.createInitial(config, random)` и `GameEngine(config, random)`
принимают генератор параметром. В коде нет `new Random()` без seed
и `Math.random()`. Это даёт воспроизводимость (проверяется `SeedTest`,
`MoveReproducibilityTest`) и понадобится в MR3 для воспроизводимого
отчёта симуляции.

### Конфиг и домен — разные слои

JSON-схема использует `boardSize`, а `GameConfig` хранит `rows` и `cols`
раздельно. Трансляцию выполняет `JsonConfigLoader` — единственное место,
где формат JSON зафиксирован. `Board` и `Position` работают с
прямоугольной моделью.

### Слои и зависимости

- `domain` не зависит ни от чего, кроме JDK.
- `config` читает JSON и конструирует `GameConfig`.
- `spawn`, `game`, `render` зависят от `domain`.
- `Main` — точка входа: связывает загрузчик, движок и рендер.

`ConfigLoader` — интерфейс, `JsonConfigLoader` — его реализация.
Если в MR3 потребуется читать симуляционный конфиг из другого источника,
появится второй загрузчик, не ломая существующий код.
