# Проект 2. Cashback Merge

Мини-игра в духе 2048 на поле `4x4`. На поле появляются плитки с кэшбэком,
две одинаковые объединяются в следующую:

```text
1% + 1% = 2%    2% + 2% = 4%    ...    16% + 16% = 32%
```

У игрока ограниченное число ходов, цель — собрать максимальный кэшбэк.

Но у проекта есть второй, продуктовый слой. По итоговой плитке начисляется
награда, и эта награда стоит компании денег. Поэтому максимальную награду
должна получать ограниченная доля игроков — например, не больше `20%`.
Проверяется это симуляцией на тысячах «игроков» до запуска акции.

Задание разбито на три merge request'а. Делай их по очереди.

## Состояние на MR3

Реализован полный продуктовый слой: таблица наград по максимальной плитке,
batch-симуляция партий с настраиваемой стратегией выбора хода, отчёт в
Markdown и проверка ограничения бюджета
`actualMaxRewardRate <= maxRewardAllowedRate`.

### Конфигурация кампании

Формат — JSON:

```json
{
  "boardSize": 4,
  "movesLimit": 100,
  "spawnRules": [
    { "cashback": "1", "probability": "0.85" },
    { "cashback": "2", "probability": "0.15" }
  ],
  "rewardTable": [
    { "cashback": "2",  "reward": "0" },
    { "cashback": "4",  "reward": "50" },
    { "cashback": "8",  "reward": "150" },
    { "cashback": "16", "reward": "500" },
    { "cashback": "32", "reward": "2000" }
  ],
  "maxRewardCashback": "32",
  "maxRewardAllowedRate": "0.20"
}
```

| Поле | Смысл | Ограничения |
|---|---|---|
| `boardSize` | размер поля `boardSize x boardSize` | положительное целое |
| `movesLimit` | лимит изменивших поле ходов | `> 0` |
| `spawnRules` | непустой массив правил появления | сумма `probability` строго `1.0` |
| `spawnRules[].cashback` | процент кэшбэка новой плитки | целое `> 0`, строкой |
| `spawnRules[].probability` | вероятность появления | десятичная строка в `(0; 1]` |
| `rewardTable` | тиры наград   | непустой, `cashback` возрастает |
| `maxRewardCashback` | порог максимальной награды | целое `> 0` |
| `maxRewardAllowedRate` | допустимая доля игроков с максимальной наградой | `[0; 1]` |

Награда за плитку — ближайший меньший тир из `rewardTable`
(`floorEntry`). Например, `12%` берёт награду за `8%`.

### Примеры отчётов

## Как работает ход

Движок разделён на два слоя.

### `SlideEngine.apply(board, direction)` — чистая функция

Компактит плитки к стороне движения, сливает соседние равные пары,
возвращает `SlideResult` с новой доской, очками за ход и признаком
`changed`. Ничего не знает про seed, лимит ходов и спавн.

Слияние идёт от края, к которому направлено движение, и каждая пара плиток
сливается не более одного раза за ход:

- `[1, 1, 1, _]` влево → `[2, 1, _, _]`
- `[1, 1, 1, 1]` влево → `[2, 2, _, _]`
- `[2, 2, 4, 4]` влево → `[4, 8, _, _]`

Плитка `32%` не сливается дальше: `32 + 32` не даёт `64`, потому что
такого тира нет в наградах.

Если ни одна плитка не сдвинулась и не слилась, `SlideEngine` возвращает
тот же объект `Board`, что был на входе, и `changed = false`.

### `GameEngine.applyMove(state, direction)` — драйвер партии

Вызывает `SlideEngine`. Если доска изменилась:

- уменьшает `movesRemaining` на один;
- прибавляет очки за слияния к `state.score`;
- спавнит ровно одну новую плитку через `WeightedSpawner`.

Если доска не изменилась — возвращает `MoveResult.unchanged(state)`
с тем же объектом `GameState`: лимит не тратится, плитка не появляется.

### Score

За каждое слияние начисляется значение получившейся плитки. Сдвиги без
слияний очков не дают. Плитка `32%` не завершает игру: партия идёт до
исчерпания лимита.

## Как работает симуляция

`SimulationRunner` для каждого «игрока» запускает независимую партию:

1. Делит мастер-`Random(seed)` на `N` детерминированных player-seed'ов.
2. Для каждого player-seed создаёт `GameEngine` и `MoveStrategy`.
3. Играет партию до исчерпания лимита или до отсутствия валидных ходов.
4. Фиксирует итоговый `maxTile`, `score` и награду по `RewardTable`.

Затем агрегирует:

- распределение максимальных плиток (`Map<Integer, Integer>`);
- распределение наград;
- средний и максимальный score;
- `actualMaxRewardRate` — доля игроков, у которых
  `maxTile >= maxRewardCashback`;
- `status = OK`, если `actualMaxRewardRate <= maxRewardAllowedRate`,
  иначе `FAILED`.

Один и тот же seed + конфиг + стратегия дают
идентичный отчёт побайтово. Проверяется тестом
`SeedTest.sameInputsProduceSameSimulationReport`.

Отчёт — эмпирический результат одного запуска. При `players = 1000` доверительный интервал
для `actualMaxRewardRate` около ±0.1%; для продуктового решения этого
достаточно, для гарантии нужно `players = 100000+`.

### Стратегии

- `random` — равновероятный выбор среди валидных направлений.
- `greedy-score` — для каждого направления считает `slide + merge`
  и выбирает ход с максимальным score; при равенстве — с наибольшим числом
  пустых клеток после хода.

## Решения, принятые в MR1–MR3

### Точная арифметика вместо `double`

Вероятности и проценты кэшбэка хранятся без потери точности:

- `Tile.cashbackPercent` — `int`;
- `Probability` — `long` в масштабе `10^9`, парсится через `BigDecimal`;
- сумма вероятностей в `GameConfig` проверяется точным сравнением
  с `Probability.SCALE`.

Это исключает классическую ловушку `0.85 + 0.15 != 1.0`.

### Иммутабельные value-объекты

`Tile`, `Position`, `Board`, `GameState`, `SlideResult`, `MoveResult`,
`SimulationResult`, `GameOutcome` — immutable. Изменяющие операции
возвращают новые значения. Это упростило тесты на merge и делает
состояние партии безопасным для параллельных симуляций.

`Board` внутри хранит `int[]`, где `0` — пустая клетка. Плюсы: нет
nullable-элементов, меньше аллокаций `Tile` в горячем пути симуляции.
Наружу — `Optional<Tile>`, `List<Tile>`, `int maxTilePercent()`.

### Разделение `SlideEngine` и `GameEngine`

Чистая логика хода отделена от stateful-драйвера с RNG. Это даёт:

- тривиальные тесты на правила merge — без seed, без конфига;
- возможность использовать `SlideEngine` из симуляции;
- контракт «no-op ход не меняет состояние» через reference equality.

### Вся случайность — через `RandomGenerator`

`GameFactory`, `GameEngine` и `SimulationRunner` принимают генератор
параметром. В коде нет `new Random()` без seed и `Math.random()`.
Это даёт воспроизводимость отчёта и тестируемость стратегий.

### Конфиг и домен — разные слои

JSON-схема использует `boardSize` и плоский `rewardTable`, а домен
хранит `rows`/`cols` и `RewardTable`. Трансляцию выполняет
`JsonCampaignLoader` — единственное место, где формат JSON
зафиксирован.

### Слои и зависимости

- `domain` не зависит ни от чего, кроме JDK.
- `config` читает JSON и конструирует `GameConfig`/`CampaignConfig`.
- `reward`, `spawn`, `game`, `strategy`, `simulation`, `report`,
  `render` зависят от `domain`.
- `Main` — точка входа, связывает загрузчик, движок и рендер.

`ConfigLoader` — интерфейс, `JsonConfigLoader` — реализация.
`MoveStrategy` — интерфейс, `RandomMoveStrategy` и
`GreedyScoreStrategy` — реализации.

## Бонусы

Реализованы:

- **Настраиваемый размер поля (4 балла).** `boardSize` читается из

- **Генеративные тесты (5 баллов).** `GenerativeTests` проверяет
  инварианты на случайных досках: сумма плиток сохраняется при
  slide/merge, число плиток не растёт, нет двойных слияний, slide
  идемпотентен без слияний. Ловит баги, которые не покрыты примерами
  из ТЗ.
- **Стратегия выбора хода (5 баллов).** `GreedyScoreStrategy`
  оценивает доступные направления по score и числу свободных клеток;
  сравнение с `random` на одинаковом seed — через
  `StrategyComparisonReportWriter`.

Не реализованы:

- **Сравнение кампаний (5 баллов).** Требует отдельного CLI-флага и
  дополнительного отчёта; вынесено за скоуп MR3.
- **Воспроизведение партии (3 балла).** Требует сериализации
  последовательности ходов; в MR3 фокус на batch-симуляции.
- **Консольная игра (3 балла).** Интерактив плохо тестируется
  автотестами, ROI ниже, чем у batch-симуляции.
